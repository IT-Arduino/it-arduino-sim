### Обратного пути нет

Форк ничего не отправляет апстриму: ни push, ни pull request. Это не
пожелание, а три независимых заслона.

**1. Репозиторий не является форком в терминах GitHub.** Он создан
самостоятельным через `gh repo create`, а не кнопкой Fork. GitHub разрешает
pull request только между репозиториями одной сети форков — из
самостоятельного репозитория PR в `davidmonterocrespo24/velxio` открыть
нельзя вовсе, такой возможности в интерфейсе нет. Это главная защита,
потому что она действует для всех и не зависит от настроек чьей-то рабочей
копии. Проверяется так:

```bash
gh repo view IT-Arduino/it-arduino-sim --json isFork,parent
```

Ответ обязан быть `{"isFork":false,"parent":null}`. Если там окажется
velxio — репозиторий создали не тем способом, и защиты нет: сеть форков
разъединяется только через поддержку GitHub либо удалением и пересозданием
репозитория.

**2. Push-адрес remote `upstream` заменён на несуществующий** — см. выше.
Заслон полезный, но слабый: он живёт в `.git/config`, не переживает свежий
клон и обходится прямым `git push <адрес>`.

**3. Хук `pre-push`** отклоняет отправку по любому адресу, где встречается
`velxio` или `davidmonterocrespo24`, — независимо от того, названо это
remote'ом или указано адресом прямо в командной строке. Хук лежит в
репозитории, но git намеренно не включает хуки из клона сам (иначе
клонирование чужого репозитория запускало бы чужой код), поэтому в каждой
рабочей копии его включают одной строкой:

```bash
git config core.hooksPath .githooks
```

Всё это — про направление «от нас к апстриму». Читать апстрим и вливать его
изменения к себе можно и нужно: на этом держится обновление форка.

## Размер Docker-образа

Замерено 2026-08-28, `docker images`, платформа linux/amd64.

| Образ | Размер |
| --- | --- |
| Исходный `Dockerfile.standalone` (апстрим, с ESP-IDF и QEMU) | **4.34 ГБ** |
| Наш `Dockerfile.avr` (только AVR) | **614 МБ** |

Разница — 3.73 ГБ, образ меньше в 7.1 раза.

**Оговорка к числу 4.34 ГБ.** Апстримовский образ из чистого клона не
собирается вообще: стадия `qemu-provider` завершается с кодом 1, если ей не
дать ни готовых `libqemu-xtensa.so` и `libqemu-riscv32.so`, ни лицензионного
ключа `VELXIO_LICENSE_KEY` для закрытого эндпоинта `velxio.dev`. Собрать QEMU
самостоятельно тоже нельзя: исходники их сборки лежат на том же закрытом
эндпоинте, а публичный `lcgamboa/qemu` по признанию самого апстрима
(`docs/BUILD-QEMU.md` в его репозитории) рабочего результата не даёт — в нём нет машины
`esp32s3-picsimlab` и четырёх устройств, от которых зависит эмуляция.

Поэтому число «до» получено сборкой с шестью файлами-заглушками вместо
бинарников QEMU: заглушки нужны только чтобы стадия 0 прошла проверку
наличия файлов. В образе нет двух библиотек `.so` и четырёх ROM-образов;
всё остальное — ESP-IDF, кросс-компиляторы Xtensa и RISC-V, `qemu-system-arm`
— на месте, а вес делают именно они. Заглушки удалены сразу после замера и в
репозиторий не попали.

Побочный, но существенный результат: `Dockerfile.avr` стадии `qemu-provider`
не содержит, поэтому **собирается из чистого клона без всяких ключей**.

## Правила работы с форком

Апстрим активен, обновления подтягиваем регулярно. Отсюда ограничения:

- Новый файл предпочтительнее правки существующего. Логика выносится в
  отдельный модуль, в чужой файл добавляется одна строка подключения.
- `frontend/src/simulation/` не трогаем — это ядро симуляции (`PinManager`,
  симуляторы CPU, `PartSimulationRegistry`), туда идут исправления апстрима.
- Формат `.vlx` не меняем: он совместим с примерами апстрима. Свои данные —
  только новыми полями верхнего уровня.
- Структура каталогов, сборщик и редактор Monaco остаются как есть.
- Каждый этап — отдельный коммит.

Фирменный стиль основного сайта называет Poppins для основного текста. Он не

кириллицу и нарисован под мелкий интерфейсный кегль, которого в панелях
симулятора большинство.

#### CSP, который ломал редактор

Content-Security-Policy из `docker/nginx.avr.conf` мы завели ради проверяемости
требования «ни одного обращения к внешним доменам». В первой редакции он
ломал две вещи, и обе видны только в консоли запущенного браузера:

- `font-src 'self'` резал шрифт иконок Monaco. Тот приходит не файлом, а
  строкой `data:font/ttf;base64` внутри собственного CSS редактора — каждая
  иконка панели инструментов рисовалась квадратом.
- `script-src` резал два скрипта, которые загрузчик AMD у Monaco и обвязка
  emscripten создают в рантайме. Прописать их хеши нельзя: они меняются при
  каждом обновлении зависимостей, и редактор ломался бы после очередного
  `npm update`, причём молча.

Ослаблены ровно две директивы: `font-src` получил `data:`, `script-src` —
`'unsafe-inline'`. Списки разрешённых хостов не тронуты. Смысл этого CSP —
запрет чужих хостов, и держат его `default-src`, `connect-src`, `img-src` и
`font-src`, а не запрет встроенных скриптов; встроенный скрипт до чужого
хоста не дотянется.

#### Тесты проверены поломкой кода

Тест, который проходит на сломанном коде, не проверяет ничего. Каждое из
четырёх ключевых свойств ломали по очереди и смотрели, упадёт ли тест:

То же сделано для тестов серверной части в репозитории сайта.

#### Вход не передаётся и не хранится

Симулятор стоит на `sim.it-arduino.ru`, сайт — на `it-arduino.ru`, API — на
`api.it-arduino.ru`. Всё это поддомены одного домена, и сессия сайта живёт в
cookie, выданной на `.it-arduino.ru`: браузер сам прикладывает её к запросу к
API, если запрос сделан с `credentials: 'include'`.

Поэтому передавать сюда нечего. Вопрос «вошёл ли пользователь» решается одним
запросом `GET /users/me`: 200 — вошёл, 401 — гость. Ни токена, ни его срока в
симуляторе нет вовсе, а cookie помечена `httpOnly` и из JavaScript не читается.

Так было не всегда. До перехода на серверные сессии (2026-09-03) сайт держал
JWT в своём `localStorage`, а чужой `localStorage` браузер не отдаёт — и
приходилось держать два механизма передачи: `postMessage` от родительской
страницы для iframe и одноразовый билет в адресной строке для прямого захода.
Вместе с ними ушли проверка origin у сообщений, вычистка билета из адреса до
сетевого запроса и разбор `exp` из токена.

Вход и выход происходят на сайте, в другой вкладке, и сигнала оттуда не
приходит. Поэтому проверка повторяется при возврате фокуса во вкладку — это
дешевле опроса по таймеру и достаточно точно: пользователь всё равно ничего не
делает в симуляторе, пока не смотрит на него.

#### Формат .vlx не тронут

В поле `data` уходит ровно то, что вернул `buildVlxPayload()`, и оттуда же
приходит обратно: сервер хранит его непрозрачным JSON. Загрузка идёт через
штатный `importVlxFile()` — тот перед записью в сторы рвёт связь с текущим
проектом (`clearCurrentProject`), иначе автосохранение приняло бы чужую схему за
правки открытого проекта и переписало бы его. Один путь кода для файла с диска и
для схемы из облака.

#### Список схем приходит без содержимого

Сто схем по мегабайту — сто мегабайт на открытие окна. `GET /circuits` отдаёт
только заголовки и даты, содержимое подтягивается по одной схеме при открытии.
Переименование тоже не пересылает содержимое обратно.

Даты сервер отдаёт наивным UTC без указания зоны (`2026-08-28T12:00:00`). Такую
строку браузер по стандарту читает как местное время, и в Москве дата съезжает
на три часа назад, поэтому перед показом дописывается `Z`.

`components/simulator/SimulatorCanvas.tsx` — почти четыре тысячи строк, и всякая

Поэтому внизу висит полоса, объясняющая почему, и подсвечивается на каждой
отклонённой правке.

#### Что осталось разрешённым

Запуск, остановка, сброс, компиляция, монитор порта, осциллограф — ради них
режим и существует. Нажатия кнопок и срабатывание датчиков идут через
`handleComponentEvent` и `updateComponentState`, это не правка схемы.

Отдельный случай — `updateComponent`. Апстрим намеренно свёл в него и диалог
свойств, и живые органы управления (`SimulatorCanvas.tsx:564`), различить их
неоткуда. Пропускаем патч, состоящий только из `properties`: без этого
потенциометр и переключатели мертвы, а изменённое сопротивление всё равно никуда
не сохраняется. Патч с координатами задерживается целиком, в том числе
смешанный, — иначе перетаскивание прошло бы в обход запрета.

`loadProjectState` не запрещён, а снимает режим: открыть свой файл .vlx или
пример можно всегда, и это уже другая схема.

#### Публикация

`is_public` в базе был с четвёртого этапа и не использовался. Теперь в «Моих
схемах» есть «Опубликовать» и «Копировать ссылку», а на сервере — отдельный
маршрут `GET /api/public/circuits/{id}` без авторизации, отдающий только
опубликованные. Отдельный, а не флаг у существующего: один эндпоинт с двумя
моделями доступа — та самая конструкция, в которой заводятся дыры. Условие
`is_public` стоит внутри запроса к базе, поэтому приватная схема не может
попасть в выборку при последующих правках кода. Приватная и несуществующая
неотличимы — обе дают 404 с одним текстом.

Сохранение из режима просмотра всегда создаёт новую схему: открытой схемой
чужая не становится, `forgetOpenCircuit()` вызывается сразу после загрузки.

Маркировка прибора остаётся латиницей: 1N4007, BC547, 74HC00, LM358. По ней

такой тест краснел бы после каждого слияния, сообщая не об ошибке, а о
появлении новой детали. Проверяется обратное — что в таблице нет ключей,
которых нет в каталоге: опечатка в идентификаторе ничего не роняет, перевод
просто молча не применяется.

### Этап 7 — плашка SPICE: перевод и лишнее предупреждение (2026-08-29)

На пустом холсте в углу висело `SPICE Warning: Error: There are no vectors
currently active.` Это не поломка: так ngspice сообщает, что решать нечего —
ни одного узла в цепи нет. Поведение снято с живого редактора:

| Что на холсте | Сообщение решателя |
| --- | --- |
| пусто | `Error: There are no vectors currently active.` |
| одна деталь, ничего не соединено | то же |
| плата без проводов | нет, решатель видит цепи питания |

То есть ученик, который только открыл редактор или только вытащил первый
резистор, получал предупреждение о схеме, которой ещё не существует.

Почему по-английски: текст плашки собирался английскими литералами прямо в

#### Правило

Пока не проведён ни один провод, сообщение «нет узлов» скрывается — это
нормальное начальное состояние. Если провода есть, а решатель всё равно
говорит «нет узлов», это уже настоящая неисправность (не собрался netlist), и
плашка показывается. Знакомые сообщения ngspice переводятся, незнакомые
выводятся как есть: выдумывать перевод строкам, которых мы не видели, значит
переводить наугад, а по исходному тексту учитель найдёт объяснение поиском.

### Этап 9 — правки по замечаниям (2026-08-29)

Четыре замечания по интерфейсу после предыдущих этапов.

#### Логические свойства — флажком, а не словом true

В метаданных апстрима логическое свойство записано двумя способами, и оба
пришлось учитывать: у пятидесяти четырёх стоит `control: "text"` при
логическом `defaultValue` (тип при этом объявлен строкой — несогласованность
апстрима), и лишь у одного, `include_flyback`, честный `control: "boolean"`.

Первые показывались текстовым полем: ученик видел слово `true` и должен был
вписать `false`, ниоткуда не узнав, что писать именно это. Второе не
редактировалось вообще — `control: "boolean"` в `isEditable` не входил.

Теперь оба случая распознаёт `isBooleanProp` и рисует флажок. Записывается
строка `'true'` или `'false'`, а не логическое значение: именно её ожидает
`DynamicComponent.tsx:157` (`value === 'true' || value === '1'`).

#### Знак «</>» дважды

`EditorPage.tsx:516` печатал литерал `&lt;/&gt;` рядом с уже нарисованной
иконкой из двух шевронов. Литерал убран, у закладки «Код» осталась иконка и
подпись — как у соседней «Схема».

#### Тэги на карточке детали

Тэги показывались как есть, по-английски. Переводится только подпись:
значение остаётся исходным, потому что по нему ищет
`ComponentRegistry.searchComponents` (`ComponentRegistry.ts:334` сравнивает
`tag.toLowerCase().includes(query)`), и подмена сломала бы находимость.

Всего тэгов 368. Переведены частые обычные слова; обозначения оставлены
латиницей — `i2c`, `spi`, `uart`, `pwm`, `74hc`, `dip14`, `ssd1306`,
`mosfet`, `npn`, `schottky` и номера приборов пишутся так и в русских
справочниках. Незнакомый тэг показывается как был.

#### Картинка ATtiny85 — воспроизвести не удалось

Проверено на живом редакторе: файл отдаётся (200, `image/svg+xml`, 8033
байта), разбирается без ошибок, элемент `<image>` в теневом дереве получает
размер 160×132, плата рисуется. Файл под контролем версий, генератор
`generate-component-svgs.cjs` его не трогает — только пишет свои и ничего не
удаляет.

Полезное из разбора: внешним файлом рисуются ровно две детали — ATtiny85
(`Attiny85Element.ts:85`) и BMP280 (`Bmp280Element.ts:54`). A4988 рисуется
встроенным SVG из метаданных и так сломаться не может. Проверка всех ссылок
вида `href="/…"` в исходниках показала, что оба файла на месте.

Наиболее вероятное объяснение — браузер закэшировал неудачную загрузку из
сеанса, когда файл ещё не был на месте. Если повторится, нужно знать, где
именно: на dev-сервере или в собранном контейнере.

### Этап 13 — ИИ-агент для схем (2026-09-04)

Задачу можно поставить словами: агент читает холст, расставляет детали из
каталога, соединяет их проводами, пишет и собирает скетч, запускает и
останавливает симуляцию. Цикл агента выполняется в браузере — шаг цикла
отправляет историю диалога на сервер сайта, получает от модели текст и

#### Предел деталей: тест был бы тавтологией

Первая версия теста «агент не поставит больше сорока деталей» просила у
заглушки модели детали по одной за шаг. При такой раскладке предел шагов
(30) сработал бы раньше предела деталей (40), и тест остановил бы прогон,
даже если предела деталей в коде не было бы вовсе — то есть не отличал бы
«предел есть» от «предела нет». Правка просит все детали одним ответом
модели за один шаг, так что срабатывает именно предел деталей, а текст
ошибки проверяется на упоминание причины — «деталей», а не «шагов».

#### Откат считает действия, а не длину истории

Дополнено на этапе 14: одного счётчика оказалось мало — см. ниже.

Кнопка «Откатить прогон» в `AgentPanel.tsx` сначала пробовала определить,
сколько отменять, по разнице длины истории холста до и после прогона. Это
ломается дважды: до первого прогона и сразу после отката длина не связана с
тем, что сделал агент, — разница дала бы случайное число вместо нуля; а
история — кольцевой буфер на фиксированное число записей, и при переполнении
старые записи вытесняются, так что разница «после минус до» молча уходит в
ноль, даже когда агент реально что-то поставил на холст. Правка считает
успешные вызовы отменяемых инструментов (`add_component`, `move_component`,
`set_component_property`, `remove_component`, `add_wire`, `remove_wire`) по
ходу прогона и откатывает не больше, чем реально лежит в истории, — иначе
откат после переполнения буфера дотянулся бы до правок, сделанных человеком
раньше агента.

#### Где живёт сервер

Обращение к модели — `POST /api/agent/chat`. Системный промпт, схема
инструментов и ключ провайдера остаются на сервере сайта
(`arduino_api/app/api/endpoints/agent.py`,
`arduino_api/app/services/agent/`), и идут туда тем же клиентом
`itArduinoApi.ts`, что уже отвечает за схемы, — `agentChat` добавлена рядом
с `getCircuit`/`createCircuit`, а не отдельным `fetch`. Маршрут доступен
только администратору и только при включённом рубильнике `AGENT_ENABLED`,
который по умолчанию выключен. При ВЫКЛЮЧЕННОМ рубильнике маршрута нет вовсе:
сервер не подключает его роутер, и любой запрос — любым методом, с любым телом —
получает тот же 404, что и несуществующий путь. При включённом рубильнике
обычный пользователь получает 403: маршрут есть, прав нет. Оба кода закреплены
серверными тестами
(`test_agent.py`: `test_disabled_switch_hides_the_route`,
`test_ordinary_user_is_rejected_when_enabled`). Ключ модели с браузером не
встречается никогда, как и токен входа в разделе о четвёртом этапе: сюда
попросту нечего передавать.

### Этап 14 — правки по итогам проверки ветки агента (2026-09-04)

Девять дефектов, найденных проверкой предыдущего этапа. Изменённых файлов
апстрима — ни одного: всё в своих файлах форка.

#### Новые файлы

| Файл | Зачем |
| --- | --- |
| `frontend/src/components/itArduinoAgent/AgentPanel.css` | Стили панели (см. таблицу новых файлов этапа 13) |

#### Что исправлено

| Что | Как |
| --- | --- |
| Ход модели с вызовами инструментов не попадал в переписку | Сообщение помощника клалось в историю только при непустом тексте, а вызовы — никогда. Модель, ответившая одними вызовами, оставляла историю вида «пользователь → результат инструмента»: `tool_call_id` результата ссылался на вызов, которого в переписке нет. Теперь ход кладётся всегда и целиком, поле `tool_calls` согласовано с серверным `AgentToolCall` |
| «Откатить прогон» отменял правки человека | Откат звал отмену по числу действий агента, а отмена снимает последнюю запись ОБЩЕЙ истории. Человек, нажавший штатную отмену между прогоном и откатом, терял свою деталь. Теперь на старте прогона запоминается рубеж — команда, на которой стоял указатель `historyIndex`, — и глубже рубежа откат не идёт. Рубеж хранится командой, а не числом: кольцевой буфер вытесняет записи с начала, и индексы съезжают |
| Ожидание появления детали короче, чем нужно | `add_component` ждал один кадр отрисовки; деталь оживает, когда подгрузится её кусок кода. Ожидание переведено на опрос с потолком — те же 100 мс и 10 с, которыми ждёт готовности сам апстрим (`DynamicComponent.tsx`) |
| Сборка всегда шла под Arduino Uno | FQBN был зашит строкой, хотя `read_canvas` честно называл модели активную плату: модель правила исправный код по чужим ошибкам. Плата берётся у холста, FQBN считает `fqbnForLanguage`, настройки — `compileOptionsForBoard` (`utils/boardCompile.ts`), то есть тем же способом, что панель инструментов и диалог прошивки |
| Предел изменений не помещался в историю отмены | Предел был только на детали (40), а история — кольцевой буфер на 50 записей: с проводами и свойствами записей выходило больше, и откат вернул бы лишь хвост. Добавлен общий предел изменяющих холст действий — 45. Предел деталей сохранён и проверяется первым, чтобы причина остановки называлась деталями, когда сыплются именно детали |
| Пункт меню видел каждый вошедший | Агент — пилот для администраторов, обычному пользователю сервер отвечает 403. Регистрация закрыта той же проверкой роли, что и галерея примеров (`lib/itArduinoRole`), и снимается при смене роли: `syncAuth` подписан и на роль, потому что она приходит вторым запросом, позже входа |
| У панели не было стилей | Классы не были определены нигде, а слот в `EditorPage` — пустой блок без размеров. Заведён свой `AgentPanel.css`, подключённый из своего компонента; вид взят у прочих окон форка, журналу отведена своя область прокрутки |
| Панель нельзя было закрыть | Добавлена кнопка закрытия; видимостью портала по-прежнему управляет `AgentPanelHost` |
| Мелочи | Комментарий про 404 при чужой роли исправлен на 403 (здесь же в FORK.md); в таблицу изменённых файлов апстрима внесён `frontend/package.json`; подпись пункта меню больше не называет чужих агентов; из теста панели убрана неиспользуемая заглушка предела шагов |

#### Запись скетча остаётся вне отмены

`write_sketch` пишет прямо в `useEditorStore`, мимо истории отмены холста.
«Откатить прогон» возвращает схему, а переписанный агентом код остаётся
переписанным. Отмена для скетча — отдельная работа: у редактора своя история,
и связать две истории в одну кнопку — не правка на полчаса. Пока об этом прямо
сказано в панели, рядом с кнопкой отката.

#### Правка человека поверх работы агента

Счётчик действий агента ограничивает, СКОЛЬКО отменять, рубеж — КУДА. Обе
границы работают на линейной истории отмены, и один случай ими не
закрывается: если человек успел сделать правку ПОСЛЕ последнего действия
агента, откат снимет её первой — отмена по-другому не умеет, она всегда
снимает верхнюю запись. Отдельная история для агента решала бы это, но она
означала бы вторую историю рядом со штатной, а действия агента должны
отменяться той же кнопкой, что и ручные.

### Этап 14 — своё расширение файлов схем (2026-09-04)

Схемы сохранялись в `.vlx` — расширение апстрима. Теперь они сохраняются в
`.itarduino`, а безымянная схема получает имя `shema.itarduino` вместо
`velxio-project.vlx`.

Открывается по-прежнему и то и другое. Файлы, сохранённые до переименования,
лежат у людей на руках, примеры апстрима тоже `.vlx`, и перестать их
открывать значило бы сломать работу без всякой причины.

**Формат внутри файла не менялся.** Поменялось только имя: содержимое как
было, так и осталось тем же JSON, что и у апстрима. Поэтому файл,
переименованный вручную в любую сторону, открывается как ни в чём не бывало.

#### Изменённые файлы апстрима

| Файл | Что | Почему |
|---|---|---|
| `frontend/src/utils/vlxFile.ts` | Расширение и основа имени по умолчанию вынесены в две константы форка | Имя сохраняемого файла собирается здесь, и больше нигде — своего места для этого в форке нет |
| `frontend/src/utils/importProject.ts` | Список принимаемых расширений вместо одного, `.itarduino` первым в `accept`, русский текст отказа | Распознавание при открытии живёт здесь; список нужен, чтобы `.vlx` продолжал открываться |
| `frontend/src/components/editor/FileExplorer.tsx` | Подпись формата в окне подтверждения берётся из имени файла | Раньше любой не-zip назывался «.vlx» — после переименования это неправда |

#### Что удалось не трогать

Строку «Импорт проекта (.vlx Velxio или .zip Wokwi)» из чужого словаря
`common2.json` править не пришлось: `fork.json` сливается последним и
перекрывает любой повторённый ключ, поэтому исправленная подпись просто
добавлена в наш словарь.

#### Тест против тихого возврата

`frontend/src/__tests__/itArduinoFileExtension.test.ts` проверяет имя
сохраняемого файла и список принимаемых расширений. Он нужен именно потому,
что обе строки живут в апстримном коде: обновление с апстрима вернёт их к
прежним значениям молча, без единой ошибки сборки, и заметить это можно было
бы только по жалобе человека, у которого схема сохранилась не тем именем.
